# 安全アライメント手法サーベイ:DPOを中心に、弱点とその改善

> ユーザー提起の論点を出発点にする:
> 「LLMの安全性アライメント確立のため DPO 等の**学習手法**の研究は多いが、
> その**学習データの統一的な作成ガイドライン**の研究はあまり行われていない」
> 本ドキュメントはこれを VLM/Jailbreak 文脈まで拡張し、各手法について
> **(a) 何を最適化するか (b) データ作成ガイドラインの成熟度 (c) 弱点 (d) 改善案** を整理する。

## 1. 手法一覧と位置づけ

```
                 学習でモデル自体を変える            推論時に外付けで守る
                 ┌───────────────────────┐        ┌───────────────────────┐
選好ベース       │ RLHF (PPO)             │        │ Guard分類器 (入出力フィルタ)│
                 │ DPO / IPO / KTO / ORPO │        │ プロンプトベース内省      │
                 │ SimPO / SPPO           │        │ (introspective defense) │
安全専用         │ Safe RLHF (二重最適化)  │        │ Constitutional/RLAIF     │
                 │ 表現工学 (circuit break)│        │ 画像前処理(敵対的浄化)   │
                 └───────────────────────┘        └───────────────────────┘
```

## 2. DPO (Direct Preference Optimization)

### 2.1 概要
- Rafailov et al. (2023)。RLHFの「報酬モデル学習→PPO」の2段階を、
  選好ペア (prompt, chosen, rejected) から直接方策を最適化する1段階に単純化。
  損失は `src/defense/train_safety_dpo.py::dpo_loss` に実装した通り。
- LLMの安全性アライメントにおいて現在最も広く使われる手法の一つ(実装が単純、
  報酬モデルのreward hackingを起こしにくい、というのが採用理由)。

### 2.2 利点
- 学習が安定・軽量(PPOのような別ネットワークのcritic不要)。
- LoRA等のPEFTと相性が良く、小規模な安全性チューニングを低コストで実施できる。
- 既存のSFTモデルに対する後付け安全パッチとして運用しやすい。

### 2.3 弱点(ユーザー指摘の核心)
1. **データ作成ガイドラインの不在**: 「chosen/rejectedをどう作るべきか」の
   標準がなく、各研究室・各社が独自基準で作成している。結果として:
   - 「安全な応答」の定義が曖昧(単純拒否 vs 説明付き拒否 vs 安全な代替提案)。
   - rejected応答の質にばらつき(明らかに悪い応答ばかりだと学習信号が弱い= 
     "easy negative problem")。
   - カテゴリ間のバランス(暴力:性的:詐欺:プライバシー…)の基準がない。
2. **過剰拒否 (over-refusal) の副作用**: 安全カテゴリに近い語彙を含むだけで
   拒否する方向に過学習しやすく、正当なユースケース(医療、創作、教育)を
   誤ってブロックする。データ作成ガイドラインがないと、この境界線の教師データが
   属人的になり、モデルごとに拒否基準がバラバラになる。
3. **単一ターン最適化中心**: 多くのDPOデータセットは1往復の(prompt, response)。
   マルチターンでの分割攻撃(docs/02の2.3節)には弱い。
4. **クロスモーダル非対応**: 素のDPOはテキストのchosen/rejectedのみを扱う設計が主流で、
   「画像入力側の安全性」(VJAのような視覚チャネル攻撃)を扱う標準的な拡張がまだ薄い。
5. **分布シフトへの脆弱性**: 学習データに存在しない難読化パターン
   (今回のshape_obfuscationのような新規表現)には汎化しにくい。

### 2.4 改善案
- **データ作成ガイドラインの標準化**(→ `docs/04_ideal_dataset_design.md` で具体案を提示)。
- **難易度カリキュラム化**: `src/dataset/dataset_optimizer.py` のような被覆最適化アルゴリズムで
  「簡単な拒否ケース」と「境界事例(hard negative)」を意図的にバランスさせる。
- **マルチモーダルDPOへの拡張**: プロンプトを `(image, text)` のペアとして扱い、
  画像側の摂動・難読化バリアントも含めて選好ペアを作る
  (`src/defense/train_safety_dpo.py --build-from-iesbench` はこの第一歩)。
- **過剰拒否対策**: 「安全に応答する良い例」と「過剰に拒否する悪い例」も
  rejectedとして混ぜ、単純な二値(拒否/実行)ではなく「適切な安全対応」を学習させる
  三値以上の選好構造(下記2.7 KTO/SimPOとの組み合わせ)。

### 2.5 関連する新しい選好最適化手法(簡易比較)

| 手法 | 特徴 | データ要件 | ガイドライン成熟度 |
|---|---|---|---|
| **DPO** | chosen/rejectedペア、参照モデル必要 | ペア比較データ | 低(前述の通り) |
| **IPO** (Azar et al.) | DPOのオーバーフィッティング傾向を正則化 | ペア比較データ | 低 |
| **KTO** (Ethayarajh et al.) | ペア不要、単一応答への good/bad ラベルのみ(プロスペクト理論に基づく) | 非ペアの2値ラベル | 低〜中(データ収集は容易だが基準は不明瞭) |
| **ORPO** | SFTと選好最適化を単一損失に統合、参照モデル不要 | ペア比較データ | 低 |
| **SimPO** | 参照モデル不要、長さ正則化で冗長応答への偏りを軽減 | ペア比較データ | 低 |
| **Safe RLHF** (Dai et al.) | 有用性報酬と安全性コストを分離し制約付き最適化 | 有用性/安全性 **別々** のアノテーション | **中**(2軸アノテーション基準を提案している点で一歩進んでいる) |
| **Constitutional AI / RLAIF** | 人手ラベルの代わりにAI自身が"憲法"(原則リスト)に基づき選好データを生成 | 原則(constitution)テキスト + AI生成の批判・修正 | **中**(原則の書き方に関する議論はあるが、画像領域への展開は薄い) |
| **表現工学 (Circuit Breakers等)** | 有害な内部表現が発火した時点で生成を中断させる、選好データ不要 | 有害/無害の代表的活性化サンプル | 低(そもそもペア比較を前提としない別系統) |

**共通の弱点**: 上記いずれも「学習アルゴリズム」の論文が中心で、
「どのように、誰が、どんな基準で、どの分布のデータを作るべきか」を規定した
**データガバナンス文書**とセットで提案されている手法はほとんどない
(Safe RLHFとConstitutional AIはやや例外的に基準を明文化している)。

### 2.6 VLM特有の防御アプローチ(比較対象)

| 手法カテゴリ | 代表例 | アプローチ | 学習要否 |
|---|---|---|---|
| 安全指示チューニング | VLGuard等 | 画像+有害指示のSFT/DPOデータで安全応答を学習 | 要学習 |
| プロンプトベース防御 | ECSO, AdaShield, 本リポジトリの introspective_defense | 画像内容をテキスト化してテキスト安全性に帰着 | Training-free |
| 画像前処理・浄化 | DiffPure系のノイズ除去、JPEG圧縮、リサイズ | 敵対的摂動やタイポグラフィの高周波成分を破壊 | Training-free(前処理) |
| 表現/特徴量検知 | 隠れ層活性化の異常検知 | 有害入力特有の内部表現パターンを検出 | 要学習(検知器) |
| クロスモーダル整合性検査 | 本リポジトリの unified_defense_pipeline | テキスト指示と画像内指示の不一致を検出 | Training-free〜軽量学習 |
| アンサンブル/多層防御 | Guard分類器 + LLM judge の直列/並列 | 単一防御の突破確率を掛け合わせて下げる | 混在 |

## 3. 「特定の攻撃だけでなく包括的にVLM Jailbreakに対応する」ための設計原則

個別の攻撃(VJA, FigStep, 敵対的摂動, ロールプレイ, …)ごとにパッチを当てる
"whack-a-mole" アプローチは持続可能でない。以下の原則を提案する。

### 原則1: モダリティ非対称性を前提にしない
テキスト安全性が強いという前提そのものが脆弱性の根源。
**すべての入力モダリティ(画像・音声・動画・埋め込みメタデータ)を、
最終的に同一の安全性判定器が扱えるテキスト的表現(または統一表現空間)へ
正規化してから判定する**(`introspective_defense.py` の設計思想を一般化)。

### 原則2: 単一チェックポイントに頼らない(スイスチーズモデル)
入力前処理・プロンプト内省・出力後検査・セッション追跡の各層で
独立に検知確率を持たせ、OR結合で全体の見逃し率を下げる
(`unified_defense_pipeline.py` で実装した3層構成が最小構成)。

### 原則3: 攻撃者の最適化を先取りする(Red-teaming as a first-class citizen)
`compare_optimize.py` のように、防御チームが自らパレート最適化を行い、
「どのパラメータ帯が盲点か」を定量化し続けるプロセスをCI/CDのように組み込む。

### 原則4: 拒否だけでなく安全な代替を提供する
過剰拒否はユーザー体験を損ない、結果として「安全策を無効化する裏技」を
ユーザー自身に探させてしまう誘因になる。安全な代替案の提示を
学習データ・評価指標の両方に組み込む(EV指標に類する「有用性を保った安全対応か」の測定)。

### 原則5: 防御の評価指標を攻撃指標と対にする
ASR/HS/EV/HRRのような攻撃側指標だけでなく、
「正当なリクエストの誤ブロック率 (False Block Rate)」を必ず併記し、
安全性と有用性のトレードオフを可視化する(`docs/04` のデータセット設計に組み込み済み)。

### 原則6: データガバナンスを学習アルゴリズムと同格に扱う
`docs/04_ideal_dataset_design.md` で具体化する「統一データ作成ガイドライン」を
モデルカード同様に**必須の付属文書**として扱う組織的ルールを設ける。
